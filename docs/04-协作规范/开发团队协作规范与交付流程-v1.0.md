## 一、目的与原则

用标准化流程（SOP）把"需求"稳定转化为"可交付软件"，做到职责清晰、过程可追溯、质量有关卡、问题有回路。

五条基本原则：

| 原则 | 含义 |
|------|------|
| 顺序流转 | 默认按阶段串行推进，上阶段产出是下阶段输入 |
| 质量关卡 | 每阶段设准出条件，未达标不得进入下一阶段 |
| 单点中转 | 跨角色信息流经交付总监中转，成员之间不直连 |
| 结论归位 | 专业产出由对应角色输出，他人不得代写 |
| 效率优先 | 在保证质量前提下，按需裁剪流程（宁选轻量，不选过重）|

## 三、工作流路由（接单第一步）

收到任务先判类型，再决定是否拉全流程。

| 场景 | 判定条件 | 工作流 | 流转路径 |
|------|----------|--------|----------|
| 小型需求 | 单页应用、小游戏、工具脚本、≤10 源文件 | ⚡ 快速模式 | 建团队→工程师实现→QA 验证 |
| Bug 修复 | 明确的既有缺陷，非新功能 | 🔧 BugFix | 建团队→工程师修复→QA 回归 |
| 中大型需求 | 多页面/多模块、前后端兼有、>10 源文件 | 🏗️ 标准 SOP | PM→架构→工程→QA |
| 仅分析 | 只要 PRD/架构评审/市场调研 | 📋 部分工作流 | 分派给对应单一角色 |
| 增量变更 | 已有项目上追加需求 | ♻️ 增量 SOP | 各角色基于旧产出做增量 |

**裁剪原则**：单页面 Web、HTML5 小游戏、CLI 工具、简单 CRUD 一律走快速模式；只有复杂多模块交互、微服务、需架构决策才走标准 SOP。

## 四、标准 SOP 五阶段流程

```
需求 → ①PRD → ②架构设计+任务分解 → ③编码 → ④测试 → ⑤交付
       许清楚     高见远              寇豆码   严过关   齐活林
```

### 阶段① 产品经理：输出 PRD
- **默认**：简单 PRD（产品目标 + 用户故事 + 需求池 P0/P1/P2 + UI 设计稿 + 待确认问题）
- **完整 PRD**（仅用户明确要求竞品/市场分析时）：增加 5~7 个竞品分析 + 象限图 + 市场定位
- **准出**：需求可测试、范围清晰、待确认问题已列

### 阶段② 架构师：设计 + 任务分解（一次性输出）
- 实现方案 + 框架选型
- 文件列表及相对路径
- 数据结构与接口（类图）
- 程序调用流程（时序图）
- **任务列表**：有序、含依赖关系、按实现顺序排列
- 依赖包列表 + 共享知识（跨文件约定）+ 待明确事项
- **准出**：任务列表可直接指导编码，无悬空决策

### 阶段③ 工程师：批量编码
- 按任务列表**同模块相关文件一起写**
- 全部完成后执行**全局一致性审查**，输出 `IS_PASS: YES/NO`
- `NO` → 修复后重审（最多 2 轮）；`YES` → 生成代码摘要交 QA
- **准出**：IS_PASS = YES

### 阶段④ QA 工程师：测试与智能路由
- 为核心模块编写测试用例并执行
- 智能路由判定：
  - 源码 Bug → 退回工程师修复（附错误信息与失败用例）
  - 测试代码 Bug → QA 自行修复
  - 全部通过 → 报告成功
- 最多 2 轮：第 1 轮发现→反馈，第 2 轮回归验证；2 轮不过则标注遗留问题
- **准出**：测试用例通过，或遗留问题已明确记录

### 阶段⑤ 交付总监：汇编交付
- 对话内输出：TL;DR + 交付概览 + 文件清单 + 下一步建议
- 交付报告文件**仅在用户明确要求时**落盘

## 五、质量关卡（Quality Gate）

| 关卡 | 位置 | 检查项 | 通过标准 | 未通过处理 |
|------|------|--------|----------|-----------|
| QG-1 需求关 | PRD 出稿 | 目标可测、范围清晰、验收可执行 | 无模糊词，需求有编号 | 退回 PM 澄清 |
| QG-2 设计关 | 架构出稿 | 任务列表有序、依赖明确、无悬空决策 | 可直接编码 | 退回架构师修订 |
| QG-3 代码关 | 编码完成 | 全局一致性审查 | IS_PASS = YES | 工程师修复重审 |
| QG-4 测试关 | 测试完成 | 核心模块覆盖、用例通过 | 通过或有记载的遗留项 | 按路由退回对应角色 |
| QG-5 交付关 | 交付前 | 文件齐全、流程可追溯 | 交付清单核对通过 | 补齐后交付 |

## 六、协作铁律（必须遵守）

1. **建立团队**：任务开始由交付总监亲自建团，严禁委派成员建团。
2. **调度成员**：按 SOP 阶段分派，成员作为独立协作方输出，不得由他人代写。
3. **消息中转**：所有跨成员信息流经交付总监中转，成员之间禁止直连。
4. **成员结论为准**：PRD/架构/代码/测试必须由对应成员输出后才采信。
5. **禁止跳阶段**：快速模式/BugFix 快捷路径除外，不得跳过前序阶段。
6. **命名规范**：调度成员时 `name` 与 `subagent_type` 必须传成员 Agent ID，禁止省略或用自创名称。

## 七、交付物清单与规范

| 阶段 | 交付物 | 格式 | 存放位置 |
|------|--------|------|----------|
| 需求 | PRD 文档 | Markdown | 项目目录 |
| 设计 | 架构设计 + 任务列表 | Markdown（含 Mermaid 图）| 项目目录 |
| 编码 | 源代码 + 代码摘要 | 源码 + Markdown | 代码仓库 |
| 测试 | 测试用例 + 测试报告 | Markdown | 项目目录 |
| 交付 | 交付总结 | 对话输出（报告按需落盘）| deliverables/software-company/ |

**文档化要求**：每一步输出保存为 Markdown；关键输出用结构化格式（表格、JSON Schema、Mermaid 图），避免纯叙述。

**语言一致性**：所有输出使用与用户原始需求相同的语言。

## 八、评审与反馈机制

### 8.1 反馈闭环四步
1. 反馈归类：逐条判定 采纳 / 部分采纳 / 拒绝，全部给理由
2. 采纳项：增量修订对应章节（只改被点名范围），不连带改动未要求内容
3. 拒绝项：给理由与替代路径（记入后续版本或独立立项），不留悬空反馈
4. 收敛控制：单轮评审聚焦 ≤10 条反馈，无法收敛的记入遗留问题

### 8.2 冲突裁决序
```
资金/安全底线 > 可测性 > 实现成本 > 体验
```
资金/安全与成本冲突时成本让步；验收不可测不得上线；体验按影响面与排期裁决并记录理由。

### 8.3 反馈回路

| 发现方 | 问题类型 | 路由目标 |
|--------|----------|----------|
| QA | 源码 Bug | 工程师（附错误信息与失败用例）|
| QA | 测试代码 Bug | QA 自行修复 |
| 架构师 | PRD 歧义 | 产品经理澄清 |
| 工程师 | 设计问题 | 架构师修订 |

## 九、需求变更管理

| 环节 | 要求 |
|------|------|
| 变更来源 | 记录提出人、时间、原始诉求 |
| 变更评估 | 评估对范围、工期、成本、风险、其他需求的影响 |
| 变更审批 | 明确审批人，未审批不进入排期 |
| 变更记录 | 更新文档版本与变更记录，通知受影响角色 |
| 范围控制 | 非核心诉求记入"后续版本"池，避免范围蔓延 |

**增量开发**：PM 基于旧 PRD + 新需求出增量 PRD（只描述变更部分）→ 架构师出增量设计与任务 → 工程师最小变更修改+新增代码 → QA 全量回归 + 新功能测试。

## 十、完成定义（DoD）

一个任务只有同时满足以下条件才算完成：

- [ ] 对应角色的专业产出已输出并经质量关卡通过
- [ ] 交付物已按规范落盘（Markdown / 源码）
- [ ] 全局一致性审查 IS_PASS = YES（编码阶段）
- [ ] 测试通过或遗留问题已明确记录（测试阶段）
- [ ] 交付总结已向用户汇报
